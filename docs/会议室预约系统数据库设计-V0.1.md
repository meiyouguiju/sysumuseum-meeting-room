## 数据库逻辑设计结论

建议 MVP 保留 **6 张核心表**：

1. `sys_user`
2. `meeting_room`
3. `booking`
4. `booking_slot`
5. `booking_audit_log`
6. `idempotency_record`

不建议 MVP 建立 `sys_role`、`sys_user_role`。当前角色固定只有 `USER`、`ADMIN`，使用 `sys_user.role_code` 单字段更直接；未来出现第三种以上角色或一人多角色时，再通过迁移拆为 RBAC 表结构。

`booking_change_log` 与 `booking_audit_log` 不应并存，建议统一为 `booking_audit_log`，避免“修改记录”和“操作审计”两套数据口径不一致。

------

## 1. `sys_user`

### 业务职责

映射中山大学统一身份认证用户，并保存系统内角色、可用状态和部门信息。

### 字段建议

| 字段               | MySQL 类型        | NULL | 默认值       | 类别      | 说明                                               |
| ------------------ | ----------------- | ---- | ------------ | --------- | -------------------------------------------------- |
| `id`               | `BIGINT UNSIGNED` | 否   | 无           | 技术      | 内部主键                                           |
| `auth_provider`    | `VARCHAR(32)`     | 否   | `'SYSU_SSO'` | 业务事实  | 认证来源；测试期可使用 `TEST`                      |
| `external_subject` | `VARCHAR(128)`    | 否   | 无           | 业务事实  | 统一身份认证提供的稳定唯一身份标识                 |
| `login_name`       | `VARCHAR(64)`     | 否   | 无           | 业务事实  | 登录账号或工号，用于展示和排查，不作为唯一身份依据 |
| `display_name`     | `VARCHAR(100)`    | 否   | 无           | 业务事实  | 当前姓名                                           |
| `department_name`  | `VARCHAR(200)`    | 是   | `NULL`       | 业务事实  | 从统一身份认证同步的部门                           |
| `role_code`        | `VARCHAR(16)`     | 否   | `'USER'`     | 业务事实  | 仅允许 `USER`、`ADMIN`                             |
| `status`           | `VARCHAR(16)`     | 否   | `'ACTIVE'`   | 业务事实  | `ACTIVE`、`DISABLED`                               |
| `last_synced_at`   | `DATETIME(0)`     | 是   | `NULL`       | 审计/技术 | 最近一次身份资料同步时间                           |
| `created_at`       | `DATETIME(0)`     | 否   | 当前时间     | 审计      | 系统建档时间                                       |
| `updated_at`       | `DATETIME(0)`     | 否   | 当前时间     | 审计      | 最后更新资料时间                                   |

### 约束与索引

- 主键：`id`
- 唯一约束：`UNIQUE(auth_provider, external_subject)`
- 可选唯一约束：`UNIQUE(auth_provider, login_name)`
  仅当校方确认账号在对应认证来源中永不复用时启用。
- 普通索引：`INDEX(status)` 不必首期建立，除非管理员确有按停用状态管理用户的页面。

### 外键建议

无外键依赖其他表；被 `booking`、`booking_audit_log`、`idempotency_record` 逻辑或物理引用。

### 设计说明

- `external_subject` 是真正的认证映射键，不能仅依赖姓名、工号展示字段。
- 不保存手机号、邮箱，符合 MVP 基线。
- 不物理删除用户；停用用户保留，用于历史预约、取消记录和审计追溯。

## 2. `meeting_room`

### 业务职责

保存会议室当前配置、状态和使用说明，同时保证历史预约始终能关联到原会议室。

### 字段建议

| 字段                 | MySQL 类型          | NULL | 默认值      | 类别     | 说明                  |
| -------------------- | ------------------- | ---- | ----------- | -------- | --------------------- |
| `id`                 | `BIGINT UNSIGNED`   | 否   | 无          | 技术     | 主键                  |
| `name`               | `VARCHAR(120)`      | 否   | 无          | 业务事实 | 会议室名称            |
| `location`           | `VARCHAR(200)`      | 否   | 无          | 业务事实 | 位置                  |
| `capacity`           | `SMALLINT UNSIGNED` | 否   | 无          | 业务事实 | 容量；仅用于超额警告  |
| `facilities_text`    | `TEXT`              | 是   | `NULL`      | 业务事实 | 设备说明              |
| `usage_notice`       | `TEXT`              | 是   | `NULL`      | 业务事实 | 使用须知              |
| `status`             | `VARCHAR(16)`       | 否   | `'ENABLED'` | 业务事实 | `ENABLED`、`DISABLED` |
| `sort_order`         | `INT`               | 否   | `0`         | 业务事实 | 日程展示顺序          |
| `created_at`         | `DATETIME(0)`       | 否   | 当前时间    | 审计     | 创建时间              |
| `created_by_user_id` | `BIGINT UNSIGNED`   | 是   | `NULL`      | 审计     | 创建管理员            |
| `updated_at`         | `DATETIME(0)`       | 否   | 当前时间    | 审计     | 最后修改时间          |
| `updated_by_user_id` | `BIGINT UNSIGNED`   | 是   | `NULL`      | 审计     | 最后修改管理员        |

### 约束与索引

- 主键：`id`
- 唯一约束：`UNIQUE(name)`
- 普通索引：`INDEX(status, sort_order, id)`

### 外键建议

- `created_by_user_id -> sys_user.id`
- `updated_by_user_id -> sys_user.id`

均使用 `RESTRICT`，不使用级联删除。

### 设计说明

MySQL 8 没有适合此处“仅启用会议室名称唯一”的通用部分唯一索引。又因会议室永不物理删除，建议名称在全表永久唯一，规则简单且可避免历史混淆。

停用不会删除会议室，不会修改历史预约的 `room_id`，因此不会破坏历史。

## 3. `booking`

### 业务职责

保存预约的业务主记录、原始预约时间、预约人、取消事实、乐观锁版本及当前状态。

### 状态设计

`booking.status` 最少使用：

- `ACTIVE`：有效预约。
- `CANCELLED`：已取消预约。

不建议保存 `FINISHED`。

“已结束”应根据：

```
status = ACTIVE 且 end_time <= 当前北京时间
```

动态计算。

理由：

- 已结束不是人工业务动作，而是时间自然流逝。
- 持久化 `FINISHED` 需要定时任务，容易与实际时间产生不一致。
- 一条历史有效预约应长期保持其原始“有效且已结束”的业务事实。
- 日程展示可根据 `start_time`、`end_time` 动态标记“正在进行”或“已结束”。

### 字段建议

| 字段                       | MySQL 类型          | NULL | 默认值     | 类别          | 说明                                             |
| -------------------------- | ------------------- | ---- | ---------- | ------------- | ------------------------------------------------ |
| `id`                       | `BIGINT UNSIGNED`   | 否   | 无         | 技术          | 主键                                             |
| `booking_no`               | `VARCHAR(32)`       | 否   | 无         | 业务事实      | 对外稳定预约编号，建议使用 ULID 等无序列冲突编号 |
| `room_id`                  | `BIGINT UNSIGNED`   | 否   | 无         | 业务事实      | 原始预约会议室                                   |
| `organizer_user_id`        | `BIGINT UNSIGNED`   | 否   | 无         | 业务事实      | 预约人；MVP 不允许代订                           |
| `organizer_name_snapshot`  | `VARCHAR(100)`      | 否   | 无         | 业务事实      | 创建时的预约人姓名快照                           |
| `subject`                  | `VARCHAR(200)`      | 否   | 无         | 业务事实      | 会议主题                                         |
| `attendee_count`           | `SMALLINT UNSIGNED` | 是   | `NULL`     | 业务事实      | 预计参会人数，超容量仅警告                       |
| `participants_text`        | `TEXT`              | 是   | `NULL`     | 业务事实      | 非结构化参会人员信息                             |
| `description`              | `TEXT`              | 是   | `NULL`     | 业务事实      | 会议说明                                         |
| `start_time`               | `DATETIME(0)`       | 否   | 无         | 业务事实      | 原始预约开始时间                                 |
| `end_time`                 | `DATETIME(0)`       | 否   | 无         | 业务事实      | 原始预约结束时间                                 |
| `status`                   | `VARCHAR(16)`       | 否   | `'ACTIVE'` | 业务事实      | `ACTIVE`、`CANCELLED`                            |
| `cancelled_at`             | `DATETIME(0)`       | 是   | `NULL`     | 业务事实      | 取消生效时间                                     |
| `cancelled_by_user_id`     | `BIGINT UNSIGNED`   | 是   | `NULL`     | 业务事实/审计 | 取消操作人                                       |
| `cancel_reason`            | `VARCHAR(500)`      | 是   | `NULL`     | 业务事实/审计 | 本人可空；管理员取消他人预约必须有值             |
| `version`                  | `INT UNSIGNED`      | 否   | `1`        | 技术          | 乐观锁版本                                       |
| `last_modified_at`         | `DATETIME(0)`       | 否   | 当前时间   | 审计          | 最近一次修改或取消时间                           |
| `last_modified_by_user_id` | `BIGINT UNSIGNED`   | 是   | `NULL`     | 审计          | 最近操作人                                       |
| `created_at`               | `DATETIME(0)`       | 否   | 当前时间   | 审计          | 创建时间                                         |
| `updated_at`               | `DATETIME(0)`       | 否   | 当前时间   | 审计          | 最后持久化更新时间                               |

### 约束与索引

- 主键：`id`
- 唯一约束：`UNIQUE(booking_no)`
- 普通索引：

| 索引                                       | 支持场景                                              |
| ------------------------------------------ | ----------------------------------------------------- |
| `INDEX(room_id, start_time, id)`           | 某会议室某日/历史预约查询                             |
| `INDEX(organizer_user_id, start_time, id)` | “我的预约”按时间查询                                  |
| `INDEX(start_time, room_id, id)`           | 管理员按日期范围导出、列表                            |
| `INDEX(status, start_time, id)`            | 管理员查询有效/已取消预约；如实际查询量不大可后置建立 |

### 外键建议

- `room_id -> meeting_room.id`
- `organizer_user_id -> sys_user.id`
- `cancelled_by_user_id -> sys_user.id`
- `last_modified_by_user_id -> sys_user.id`

全部使用 `RESTRICT`，不允许删除被引用的用户或会议室。

### 重要说明

`booking` 保存的是预约的完整业务事实和历史，取消后仍保留原始 `start_time`、`end_time`、会议室和主题，不能因为释放未来槽位而改写原预约时间。

## 4. `booking_slot`

### 业务职责

这是会议室资源占用的运行时表。每条记录代表某会议室在某个 30 分钟槽内不可被再次预约。

它是并发正确性的最终防线，不是预约历史主表。

### 是否保存 `slot_end`

不建议保存 `slot_end`。

原因：

- 时间粒度永久固定为 30 分钟。
- `slot_end = slot_start + 30 分钟`，属于可推导值。
- 保存会引入不必要的冗余和一致性风险。
- 未来若粒度改变，应通过业务版本迁移处理，而不是提前为未知需求冗余存储。

### 字段建议

| 字段              | MySQL 类型        | NULL | 默认值     | 类别          | 说明                                    |
| ----------------- | ----------------- | ---- | ---------- | ------------- | --------------------------------------- |
| `id`              | `BIGINT UNSIGNED` | 否   | 无         | 技术          | 主键                                    |
| `booking_id`      | `BIGINT UNSIGNED` | 否   | 无         | 业务事实      | 对应预约                                |
| `room_id`         | `BIGINT UNSIGNED` | 否   | 无         | 业务事实      | 冗余保存，直接支撑唯一冲突约束          |
| `slot_start`      | `DATETIME(0)`     | 否   | 无         | 业务事实      | 槽开始时间                              |
| `occupancy_state` | `VARCHAR(24)`     | 否   | `'ACTIVE'` | 业务事实/技术 | `ACTIVE`、`CANCELLED_CURRENT_SLOT_HOLD` |
| `created_at`      | `DATETIME(0)`     | 否   | 当前时间   | 审计/技术     | 槽创建时间                              |
| `updated_at`      | `DATETIME(0)`     | 否   | 当前时间   | 审计/技术     | 当前槽状态修改时间                      |

### 约束与索引

- 主键：`id`
- 关键唯一约束：`UNIQUE(room_id, slot_start)`
- 建议唯一约束：`UNIQUE(booking_id, slot_start)`
- 普通索引：`INDEX(slot_start, room_id, booking_id)`

其中：

- `UNIQUE(room_id, slot_start)`：并发预约冲突的最终保障。
- `UNIQUE(booking_id, slot_start)`：防止同一预约因程序错误重复生成同一槽。
- `INDEX(slot_start, room_id, booking_id)`：支持某日所有会议室日程查询。

### 外键建议

- `booking_id -> booking.id`
- `room_id -> meeting_room.id`

使用 `RESTRICT`，不使用级联删除。

### 进行中预约取消的数据生命周期

以预约为 10:00～12:00，用户在 10:12 取消为例：

| 时间点         | `booking`              | `booking_slot`                                               |
| -------------- | ---------------------- | ------------------------------------------------------------ |
| 创建成功       | `ACTIVE`               | 10:00、10:30、11:00、11:30 均为 `ACTIVE`                     |
| 10:12 取消事务 | 更新为 `CANCELLED`     | 删除 10:30、11:00、11:30；保留 10:00                         |
| 同一取消事务   | 记录 `cancelled_at` 等 | 将 10:00 更新为 `CANCELLED_CURRENT_SLOT_HOLD`                |
| 10:30 后       | 仍为 `CANCELLED`       | 后台清理任务删除 10:00 保留槽                                |
| 长期历史       | 保留                   | 由 `booking` 与 `booking_audit_log` 保存，不依赖 `booking_slot` |

清理任务建议每 1～5 分钟执行一次，删除所有：

```
slot_start < 当前所在30分钟槽开始时间
```

的 `booking_slot` 行。

这样：

- 当前槽在结束前继续阻塞占用；
- 下一完整时间槽立即可被预约；
- 过去槽不会无限增长；
- 已结束预约仍可通过 `booking` 记录展示在当天日程中；
- 审计历史不依赖操作型时间槽表。

在公共日程中，`CANCELLED_CURRENT_SLOT_HOLD` 应仅表现为“不可预约/已占用到本槽结束”，不展示已取消预约的会议主题或参会信息。

## 5. `booking_audit_log`

### 业务职责

统一记录创建、修改、取消操作，满足：

- 管理员修改/取消他人预约的完整审计。
- 每次修改前后完整内容保存。
- 取消时释放了哪些槽、保留了哪个当前槽的追溯。
- 长期历史留存。

### 结构化字段还是 JSON

建议采用：

```
固定审计元数据字段 + before_json + after_json
```

而不是为每个预约字段建立一列历史表。

理由：

- MVP 预约字段数量有限，但未来可能增加。
- “保存每次修改前后完整内容”最适合不可变 JSON 快照。
- 审计的主要用途是追溯，不是复杂分析。
- 若未来需要对审计字段做统计，可再补充结构化派生字段。

### 字段建议

| 字段                   | MySQL 类型        | NULL | 默认值   | 类别          | 说明                                   |
| ---------------------- | ----------------- | ---- | -------- | ------------- | -------------------------------------- |
| `id`                   | `BIGINT UNSIGNED` | 否   | 无       | 技术          | 主键                                   |
| `booking_id`           | `BIGINT UNSIGNED` | 否   | 无       | 业务事实      | 被操作预约                             |
| `operation_type`       | `VARCHAR(24)`     | 否   | 无       | 业务事实      | `CREATE`、`UPDATE`、`CANCEL`           |
| `actor_user_id`        | `BIGINT UNSIGNED` | 否   | 无       | 审计          | 操作人                                 |
| `actor_role_snapshot`  | `VARCHAR(16)`     | 否   | 无       | 审计          | 操作当时角色                           |
| `target_owner_user_id` | `BIGINT UNSIGNED` | 否   | 无       | 审计          | 预约归属人，便于识别管理员操作他人记录 |
| `reason`               | `VARCHAR(500)`    | 是   | `NULL`   | 业务事实/审计 | 管理员修改他人或取消他人预约时必填     |
| `version_before`       | `INT UNSIGNED`    | 是   | `NULL`   | 审计/技术     | 操作前版本；创建可空                   |
| `version_after`        | `INT UNSIGNED`    | 否   | 无       | 审计/技术     | 操作后版本                             |
| `before_json`          | `JSON`            | 是   | `NULL`   | 审计          | 修改前完整预约快照；创建可空           |
| `after_json`           | `JSON`            | 否   | 无       | 审计          | 修改后完整预约快照                     |
| `slot_change_json`     | `JSON`            | 是   | `NULL`   | 审计          | 新增、删除、保留槽信息                 |
| `occurred_at`          | `DATETIME(0)`     | 否   | 当前时间 | 审计          | 操作完成时间                           |

`before_json`、`after_json` 应包含预约全部业务字段；取消后的 `after_json` 必须保留原始预约时间和取消信息。

### 约束与索引

- 主键：`id`
- 普通索引：

| 索引                                     | 支持场景             |
| ---------------------------------------- | -------------------- |
| `INDEX(booking_id, occurred_at, id)`     | 预约完整变更历史     |
| `INDEX(actor_user_id, occurred_at, id)`  | 管理员操作审计       |
| `INDEX(operation_type, occurred_at, id)` | 取消、修改等审计排查 |

不建议对 JSON 内部字段建立索引。

### 外键建议

- `booking_id -> booking.id`
- `actor_user_id -> sys_user.id`
- `target_owner_user_id -> sys_user.id`

审计记录永不物理删除。

## 6. `idempotency_record`

### 业务职责

支持“创建预约”的 24 小时严格幂等、网络超时结果查询以及重复提交保护。

该表只服务于创建预约，不建议泛化为所有 API 的幂等中心。

### 字段建议

| 字段                   | MySQL 类型          | NULL | 默认值             | 类别     | 说明                                |
| ---------------------- | ------------------- | ---- | ------------------ | -------- | ----------------------------------- |
| `id`                   | `BIGINT UNSIGNED`   | 否   | 无                 | 技术     | 主键                                |
| `operation_type`       | `VARCHAR(32)`       | 否   | `'CREATE_BOOKING'` | 技术     | 预留操作隔离；MVP 固定创建预约      |
| `user_id`              | `BIGINT UNSIGNED`   | 否   | 无                 | 业务事实 | 请求用户                            |
| `idempotency_key`      | `VARCHAR(128)`      | 否   | 无                 | 技术     | 客户端本次创建请求的唯一键          |
| `request_hash`         | `BINARY(32)`        | 否   | 无                 | 技术     | 规范化请求体的 SHA-256 摘要         |
| `processing_status`    | `VARCHAR(16)`       | 否   | `'PROCESSING'`     | 技术     | `PROCESSING`、`SUCCEEDED`、`FAILED` |
| `booking_id`           | `BIGINT UNSIGNED`   | 是   | `NULL`             | 业务事实 | 成功创建的预约                      |
| `response_http_status` | `SMALLINT UNSIGNED` | 是   | `NULL`             | 技术     | 首次完成结果的 HTTP 状态码          |
| `response_body`        | `JSON`              | 是   | `NULL`             | 技术     | 首次完成的标准响应体                |
| `failure_code`         | `VARCHAR(64)`       | 是   | `NULL`             | 技术     | 失败时的稳定业务错误码              |
| `completed_at`         | `DATETIME(0)`       | 是   | `NULL`             | 技术     | 首次处理完成时间                    |
| `created_at`           | `DATETIME(0)`       | 否   | 当前时间           | 技术     | 首次收到请求时间                    |
| `expires_at`           | `DATETIME(0)`       | 否   | 无                 | 技术     | 固定为创建后 24 小时                |
| `updated_at`           | `DATETIME(0)`       | 否   | 当前时间           | 技术     | 状态最后更新时间                    |

### 约束与索引

- 主键：`id`
- 唯一约束：`UNIQUE(operation_type, user_id, idempotency_key)`
- 普通索引：

| 索引                              | 支持场景               |
| --------------------------------- | ---------------------- |
| `INDEX(user_id, idempotency_key)` | 原幂等键的结果查询     |
| `INDEX(expires_at)`               | 定时清理过期技术记录   |
| `INDEX(booking_id)`               | 排查创建结果与预约关联 |

如果唯一约束已使用 `(operation_type, user_id, idempotency_key)`，额外的 `(user_id, idempotency_key)` 仅在查询不带操作类型时才需要；API 若固定使用 `CREATE_BOOKING`，可不额外建立以避免冗余。

### 请求正在处理时的并发处理

建议把“创建幂等记录、写预约、写槽、写成功响应”放在同一个数据库事务中：

1. 请求尝试插入 `(operation_type, user_id, idempotency_key)`。
2. 首个请求获得唯一键写入权，在事务内暂为 `PROCESSING`。
3. 同事务内创建 `booking`、批量插入 `booking_slot`、写审计日志。
4. 同事务内把幂等记录更新为 `SUCCEEDED` 并保存首次响应。
5. 最后一次性提交。

第二个相同请求到达时：

- 会因唯一约束等待第一个事务结束。
- 第一个事务成功提交后，第二个请求读取 `SUCCEEDED` 和相同 `request_hash`，直接返回首次响应。
- 如果 `request_hash` 不同，拒绝请求，不创建第二条预约。
- 第一个事务因冲突或校验失败而回滚时，不保留错误的处理中记录；第二个请求可成为新的首次处理请求。
- 如果第二个请求在等待首个事务时自身超时，应返回“处理结果暂时无法确认/仍在处理”，客户端必须使用原 `Idempotency-Key` 查询，不能换新键重新创建。

实际完成后，数据库中正常可见的记录应为 `SUCCEEDED` 或 `FAILED`；`PROCESSING` 主要是事务内中间状态。这样避免“预约已提交但幂等记录仍处理中”的跨事务不一致。

### 数据保留

- `idempotency_record` 是技术数据。
- 在 `expires_at` 后可以定期物理删除。
- 删除前需确保不影响仍在处理的事务；按 `expires_at < 当前时间` 清理即可。
- 24 小时后复用同一个 Key 不建议，但系统可按“旧记录已过期并清理”视为新请求。

## 外键策略

本项目建议使用真实 MySQL `FOREIGN KEY`，而不是仅逻辑关联。

原因：

- 系统规模小、写入量有限。
- 用户、会议室、预约均要求长期保留，不存在高频物理删除。
- 外键能防止错误预约到不存在用户或会议室。
- 审计和占用槽的引用完整性比微小写入性能损失更重要。

约束原则：

- 使用 InnoDB。
- 全部使用 `RESTRICT` 或等价“禁止删除”策略。
- 禁止 `ON DELETE CASCADE`。
- 先插主记录，再插子记录；删除只允许清理 `booking_slot` 与过期 `idempotency_record`。
- 不物理删除 `sys_user`、`meeting_room`、`booking`、`booking_audit_log`。

## 事务边界建议

### 创建预约

单事务完成：

1. 锁定或插入 `idempotency_record`。
2. 校验用户、会议室状态、14 天、时间粒度、时长和跨日规则。
3. 插入 `booking`。
4. 批量插入全部 `booking_slot`。
5. 唯一约束冲突时回滚，并返回预约冲突。
6. 插入 `booking_audit_log` 的 `CREATE` 快照。
7. 更新幂等记录为首次最终响应。
8. 提交。

### 修改预约

单事务完成：

1. 按 `booking.id` 锁定目标预约。
2. 基于 `version` 校验乐观锁版本。
3. 校验对象权限和修改时间规则。
4. 保存修改前完整快照。
5. 如果会议室或时间变化，删除仍由该预约占用的未来槽，再插入新槽。
6. 若新槽唯一约束冲突，整体回滚，原槽不变。
7. 更新预约、递增 `version`。
8. 写入 `booking_audit_log` 的 `UPDATE` 前后快照及槽变化。
9. 提交。

### 取消预约

单事务完成：

1. 锁定预约。
2. 校验状态、权限、是否已经结束，以及管理员取消他人是否提供原因。
3. 保存取消前快照。
4. 更新 `booking.status = CANCELLED` 及取消字段，递增 `version`。
5. 未开始：删除全部 `booking_slot`。
6. 进行中：删除后续槽；将当前槽更新为 `CANCELLED_CURRENT_SLOT_HOLD`。
7. 写入 `booking_audit_log` 的 `CANCEL` 前后快照和槽变化。
8. 提交。

## 潜在设计风险

1. “08:30～17:30 仅重点展示，但全天可预约”意味着系统实际支持 00:00～24:00 的 48 个时间槽。桌面端重点展示可以成立，但手机端必须提供非重点时段的明确选择入口。
2. `booking_slot` 是运行时占用表，不是历史明细表。过去槽被清理后，历史日程必须以 `booking.start_time/end_time` 生成，而不是依赖槽表。
3. 幂等响应体必须稳定。首次成功响应中不应包含会随时间变化的字段，否则重复查询无法返回语义一致的“首次结果”。
4. 管理员可修改任意预约，但基线未明确“管理员修改已经开始预约的时间范围”应如何处理。若允许将已开始预约改到其他时间，可能影响已实际使用的时段和审计解释。建议技术实现先允许管理员修改进行中预约的非时间字段；涉及会议室或时间变更时，要求目标预约尚未开始，除非产品明确允许管理员覆盖这一规则。
5. 外键结合操作型槽清理时，必须严格遵守删除顺序：先删除 `booking_slot`，不能删除 `booking`。
6. 管理员导出“固定字段与固定范围”尚未定义，但不阻塞数据库设计；当前索引已能支持以日期范围、会议室和状态为条件导出。
