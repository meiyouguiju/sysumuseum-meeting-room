# 会议室预约系统前端产品与交互设计 V1.0

文档版本：V1.0  
状态：正式基线  
适用项目：中山大学校史馆会议室预约系统  
适用阶段：Frontend F0～F6  
前端技术栈：Vue 3 + TypeScript + Vite  
后端基线：`backend-mvp-v1`

---

# 1. 文档目的

本文用于冻结会议室预约系统前端 V1.0 的产品结构、页面、核心交互、桌面端与手机端布局、组件边界和开发阶段。

后续前端实现应以本文和以下已冻结后端文档为事实来源：

- `会议室预约系统MVP业务规则确认文档-V1.0.md`
- `会议室预约系统REST-API设计-V1.0.md`

原则：

1. 后端业务规则与 REST 契约优先。
2. 前端不得为了实现方便擅自修改已经冻结的后端规则。
3. 如前端设计与 REST 契约发生冲突，优先调整前端。
4. V1 以业务正确性、可维护性和内部使用效率优先，不追求不必要的复杂交互。

---

# 2. 产品目标

系统用于中山大学校史馆内部会议室预约。

核心目标：

- 用户能够快速查看不同会议室在某一天的空闲和占用情况；
- 用户能够直接从日程表创建预约；
- 用户能够管理自己的预约；
- 管理员能够管理全部预约和会议室；
- 桌面端优先提供高信息密度二维日程；
- 手机端重新组织信息，不强行缩小桌面二维表。

---

# 3. 已冻结业务规则

前端必须遵守以下后端业务规则：

- 时间粒度固定为 30 分钟；
- 新预约允许范围为服务器北京时间今天起连续 14 个自然日；
- 08:30～17:30 仅为重点展示时段，不是预约限制；
- 周末、节假日、午休、17:30 后均允许预约；
- 最短预约 30 分钟；
- 最长预约 5 小时；
- 不允许跨日；
- 用户可以看到会议室及公共预约主题、预约人姓名；
- 参会人员名单仅预约本人和管理员可见；
- 普通用户可以创建预约；
- 普通用户只能修改本人未开始预约；
- 普通用户可以取消本人尚未结束的预约；
- 进行中预约允许取消；
- 进行中取消后，当前 30 分钟槽继续占用，后续槽释放；
- 管理员可以管理会议室；
- 管理员可以修改和取消任意符合状态要求的预约；
- 管理员修改或取消他人预约时必须填写原因；
- 停用会议室仍然可见；
- 停用会议室历史预约保留；
- 停用会议室已有未来预约不会自动取消；
- 停用会议室不能创建新预约；
- 停用会议室不能作为修改预约的新目标；
- V1 不使用 WebSocket 自动刷新；
- 创建、修改、取消、冲突和切换日期后重新获取日程；
- 创建预约必须使用严格 `Idempotency-Key`。

前端 V1.0 分为三个业务域：

```text

├─ 我的预约
│  ├─ 查看本人预约

│  ├─ 修改本人预约
│  └─ 取消本人预约

└─ 管理
```

```text
预约管理 | 会议室管理
```

# 7. 桌面端核心日程

桌面端核心是：

```text
会议室 × 时间
```

纵轴：

```text
会议室
```

横轴：

```text
一天的时间
```

固定 30 分钟一个槽，一天共 48 个时间槽。

示意：

```text
             08:30     09:00     09:30     10:00
┌──────────┬────────┬────────┬────────┬────────┐
│ 会议室   │        │        │        │        │
├──────────┼────────┼────────┼────────┼────────┤
│ 2A会议室 │        │ 项目讨论会████████       │
├──────────┼────────┼────────┼────────┼────────┤
│ 2B会议室 │        │        │        │        │
└──────────┴────────┴────────┴────────┴────────┘
```

---

# 8. 日程工具栏

日程顶部包括：

- 前一天；
- 当前日期；
- 后一天；
- 今天；
- 日期选择器；
- 重点时段/全天视图切换或定位能力。

建议文案：

```text
< 2026年8月24日 周一 >
[今天]
```

可显示：

```text
重点时段：08:30～17:30
```

不要称为：

```text
工作时间
```

以免误导用户认为其他时间不可预约。

---

# 9. 时间轴规则

一天始终存在完整 48 个 30 分钟槽。

推荐：

- 每 30 分钟一条细分隔线；
- 每整点一条更明显分隔线；
- 时间 Header 固定；
- 左侧会议室列固定；
- 时间区域横向滚动；
- 页面整体允许纵向滚动。

推荐实现：

```text
顶部 Header sticky
左侧 Room column sticky
```

---

# 10. 重点时段表现

08:30～17:30：

- 正常背景；
- 默认视口优先定位到该区域。

其它时段：

- 使用较弱的灰色背景；
- 依然可点击；
- 依然允许预约。

不得将非重点时段实现为 disabled。

---

# 11. 会议室行

左侧会议室区域建议展示：

```text
博物馆2A会议室
100人
```

桌面日程的会议室行以 Schedule API 返回的 `ScheduleRoom` 为准，V1 显示会议室名称、容量和状态。`location`、`facilitiesText`、`usageNotice` 等完整会议室信息属于 Room 资源，不要求在二维日程行中展示。

如果会议室停用：

```text
博物馆2A会议室
100人 · 已停用
```

可使用：

- 灰色背景；
- 纹理；
- 明确“已停用”文字。

停用会议室的历史和已有预约仍必须继续显示。

---

# 12. 预约块

预约块优先展示：

1. 会议主题；
2. 预约人；
3. 开始时间～结束时间；
4. 展示状态。

例如：

```text
数字校史馆项目讨论会
张三
09:00–10:30
进行中
```

状态来源：

```text
UPCOMING
IN_PROGRESS
ENDED
```

前端映射文案可为：

```text
未开始
进行中
已结束
```

公共日程不显示已取消预约。

---

# 13. 窄预约块的信息策略

30 分钟预约宽度可能非常窄。

原则：

> 所有信息必须可访问，但不要求任何宽度都同时完整显示。

预约块采用渐进展示。

宽度足够：

```text
主题
预约人
时间
状态
```

宽度较窄：

```text
主题
状态
```

详细内容通过点击后查看。

不得因为文字放不下而强行把一个 30 分钟槽撑宽。

---

# 14. 不只使用颜色表达状态

状态必须采用：

```text
颜色 + 文字 / 标签 / 纹理
```

例如：

进行中：

```text
颜色 + “进行中”
```

已结束：

```text
弱化颜色 + “已结束”
```

停用会议室：

```text
灰色/纹理 + “已停用”
```

保留不可用槽：

```text
纹理 + “暂不可预约”
```

空闲槽：

```text
Hover 显示 “+ 预约”
```

不得仅依赖颜色区分。

---

# 15. “我的预约”在日程中的处理

V1 日程公共预约数据不可靠提供预约归属判断所需的 `organizerUserId` 或 `isMine`。

因此 V1 冻结：

> 日程预约块暂不强制显示“我的预约”标签。

不得使用：

```text
organizerName == currentUser.displayName
```

判断本人，因为存在重名风险。

本人预约管理集中在“我的预约”页面。

未来如果产品强需求再正式评审 API 是否增加归属字段。

---

# 16. unavailableSlots

后端 Schedule 可能返回：

```text
unavailableSlots
```

当前原因：

```text
CANCELLED_CURRENT_SLOT_HOLD
```

表示进行中预约取消后，当前 30 分钟槽仍然继续占用。

前端表现：

```text
暂不可预约
```

推荐：

- 灰色；
- 斜线纹理；
- 无预约主题；
- 不泄露原预约人信息。

该槽不能发起新预约。

---

# 17. 空闲槽发起预约

V1 不实现拖拽选择预约时段。

原因：

- 增加桌面拖拽复杂度；
- 增加手机触摸复杂度；
- 容易与滚动冲突；
- 无障碍和误操作成本高；
- 内部系统收益有限。

V1 采用：

```text
点击空闲时间槽
```

Hover：

```text
+ 预约
```

点击后打开创建预约界面。

默认带入：

- 当前会议室；
- 当前日期；
- 当前开始时间；
- 默认结束时间 = 开始时间 + 30 分钟。

---

# 18. 创建预约交互

## 18.1 桌面端

使用右侧 Drawer。

原因：

- 保持日程上下文；
- 表单空间足够；
- 比小型 Modal 更适合多个字段。

## 18.2 手机端

使用：

- 全屏 Dialog；
- 或占据主要屏幕的 Bottom Sheet。

桌面和手机共享同一 ReservationForm 业务模型。

---

# 19. 创建预约字段

创建表单字段严格使用后端契约：

```text
会议室 *
会议主题 *
开始时间 *
结束时间 *
预计人数
参会人员
说明
```

对应：

```text
roomId
subject
startTime
endTime
attendeeCount
participantsText
description
```

V1 不新增：

- 联系电话；
- 部门；
- 会议分类；
- 审批人；
- 会议颜色；
- 自定义备注字段。

---

# 20. 容量超限

如果：

```text
attendeeCount > room.capacity
```

前端可以提前提示：

```text
预计人数超过会议室容量，请确认。
```

但不得阻止提交。

后端容量超限为 Warning，不是业务失败。

---

# 21. 创建预约严格幂等

每次新打开一个创建表单：

```text
生成新的 Idempotency-Key
```

同一次创建流程必须始终使用同一个 Key。

网络超时：

- 不能认为创建失败；
- 不能更换新 Key 重提；
- 必须使用原 Key 查询幂等结果。

创建成功或确定性失败后，本次创建流程结束。

下一次新创建才生成新 Key。

---

# 22. 创建成功

成功后：

1. 显示成功提示；
2. 关闭创建 Drawer；
3. 重新获取相关日程；
4. 重新获取我的预约；
5. 不通过前端手工插入虚拟预约来代替服务器刷新。

服务器数据是最终事实来源。

---

# 23. 创建冲突

如果返回时间槽冲突：

前端：

1. 保留主题、参会人员、说明等表单内容；
2. 提示该时间段已被其他用户预约；
3. 重新获取当前日期日程；
4. 引导用户修改会议室或时间。

不得自动重复提交。

---

# 26. 普通用户修改预约

普通用户仅允许修改：

```text
本人
ACTIVE
未开始
```

点击：

```text
修改预约
```

复用 ReservationForm。

编辑模式必须基于完整 BookingDetail。

修改请求按照后端契约提交完整修改体。

成功后：

- 刷新预约详情；
- 刷新我的预约；
- 刷新旧日期日程；
- 如日期发生变化，刷新新日期日程。

---

# 27. 普通用户取消预约

取消前必须二次确认。

未开始：

```text
确定取消该预约吗？
```

进行中：

必须额外说明：

```text
该预约正在进行。
取消后当前 30 分钟时间槽仍继续占用，
后续尚未开始的时间槽将释放。
```

普通用户取消原因可选。

---

# 28. 我的预约页面

V1 采用：

> 单一分页列表。

不采用：

```text
即将开始 | 进行中 | 历史
```

原因：

后端 `/me/bookings` 当前只提供分页，没有状态筛选参数。前端不能只拿当前页数据进行过滤并误导用户。

列表每条显示：

```text
会议主题
会议室
日期
开始时间～结束时间
状态
```

操作根据状态显示：

```text
查看
修改
取消
```

# 30. 管理员查看预约详情

管理员复用普通 BookingDetail。

管理员可以读取任意预约完整详情。

不建立额外管理员详情 DTO 或独立详情模型。

# 31. 管理员修改预约

## 31.1 未开始预约

管理员可修改：

```text
会议室
主题
开始时间
结束时间
预计人数
参会人员
说明
```

如果修改他人的预约：

```text
修改原因 *
```

必填。

如果修改自己的预约：

```text
修改原因
```

可选。

## 31.2 进行中预约

管理员只能修改：

```text
主题
预计人数
参会人员
说明
原因
```

不得提交：

```text
roomId
startTime
endTime
```

即使值没有变化也不能提交。

因此实现层需要使用与未开始预约不同的 Request Body。

## 31.3 已结束或已取消

不可修改。

# 32. 管理员取消预约

管理员可以取消符合状态规则的预约。

如果取消他人预约：

```text
取消原因 *
```

必填。

进行中预约取消规则和普通用户一致：

- 当前槽继续占用；
- 后续槽释放。

取消前必须二次确认。

# 35. 新增会议室


# 53. 前端 V1.0 冻结决策

以下视为正式冻结：

1. `/schedule` 为首页；
2. 桌面采用“会议室 × 时间”二维矩阵；
3. 30 分钟一个槽；
4. 全天 48 个槽存在；
5. 默认重点展示 08:30～17:30；
6. 左会议室列固定；
7. 顶部时间 Header 固定；
8. 点击空闲槽创建；
9. V1 不做拖拽预约；
10. 创建/编辑复用 ReservationForm；
11. 桌面创建/详情优先 Drawer；
12. 公共预约详情只展示 Schedule 摘要；
13. 完整 BookingDetail 仅本人和管理员读取；
14. 日程 V1 不显示“我的预约”标签；
15. 我的预约采用单一分页列表；
16. 管理员预约管理 V1 不做筛选栏；
17. CSV 日期范围独立于管理员预约列表；
18. 手机采用“日期 → 会议室 → 纵向时间轴”；
19. Server State 使用 TanStack Vue Query；
20. Pinia 不重复缓存后端 Server State；
21. Mutation 后重新从后端获取事实数据；
22. 不为前端方便修改已冻结后端 REST 契约。

本文为前端 V1.0 正式基线。

后续如果发现：

必须先重新评审，再修改本文版本。
