# 会议室预约系统数据库物理设计

文档版本：V0.1.1  
状态：与数据库逻辑设计 V0.2 对齐  
迁移脚本：[V1__init_schema.sql](../backend/src/main/resources/db/migration/V1__init_schema.sql)

## 1. 物理实现范围

首个 Flyway 迁移创建六张表：`sys_user`、`meeting_room`、`booking`、`booking_slot`、`booking_audit_log`、`idempotency_record`。不创建测试数据、正式用户、管理员或会议室初始数据。

所有表使用 `ENGINE=InnoDB`、`DEFAULT CHARSET=utf8mb4` 和 `utf8mb4_0900_ai_ci` 排序规则。主键和逻辑关联 ID 统一为 `BIGINT UNSIGNED`，主键采用 `AUTO_INCREMENT`。

## 2. 字段与时间策略

- 预约开始、结束、取消、审计、幂等有效期等时间均使用 `DATETIME(0)`，不使用 `TIMESTAMP` 保存预约业务时间。
- 业务时区固定为 `Asia/Shanghai`；Java 使用 `LocalDateTime` 映射业务时间，连接和序列化环境必须统一时区。
- `created_at`、`updated_at` 等维护字段使用 `DATETIME(0)` 与 `CURRENT_TIMESTAMP` 默认值；`updated_at`、`last_modified_at` 使用 `ON UPDATE CURRENT_TIMESTAMP` 保持维护时间。
- `booking.status` 仅持久化 `ACTIVE`、`CANCELLED`。已结束状态由 `end_time` 与当前北京时间动态计算，不持久化 `FINISHED`。

## 3. 主键、唯一约束和普通索引

| 表 | 主键 | 唯一约束 | 普通索引 |
| --- | --- | --- | --- |
| `sys_user` | `id` | `(auth_provider, external_subject)` | 无 |
| `meeting_room` | `id` | `(name)` | `(status, sort_order, id)` |
| `booking` | `id` | `(booking_no)` | `(room_id, start_time, id)`、`(organizer_user_id, start_time, id)`、`(start_time, room_id, id)`、`(status, start_time, id)` |
| `booking_slot` | `id` | `(room_id, slot_start)`、`(booking_id, slot_start)` | `(slot_start, room_id, booking_id)` |
| `booking_audit_log` | `id` | 无 | `(booking_id, occurred_at, id)`、`(actor_user_id, occurred_at, id)`、`(operation_type, occurred_at, id)` |
| `idempotency_record` | `id` | `(operation_type, user_id, idempotency_key)` | `(expires_at)` |

所有通过幂等键查询首次创建结果的接口必须带固定条件 `operation_type='CREATE_BOOKING'`、`user_id` 和 `idempotency_key`，以使用现有联合唯一索引；不建立冗余的 `(user_id, idempotency_key)` 索引。

`booking_slot` 的 `(room_id, slot_start)` 唯一约束是最终并发冲突裁决：两个并发事务尝试占用同一会议室同一 30 分钟槽时，只有一个事务能提交。应用层预检查只用于改善体验，不能取代该约束。

## 4. CHECK 约束

MySQL 8 使用 `CHECK`，不用 `ENUM`，以便未来状态扩展通过新 Flyway 迁移显式调整约束。V1 包含：

| 表 | 受限字段 | 合法值 |
| --- | --- | --- |
| `sys_user` | `role_code` | `USER`、`ADMIN` |
| `sys_user` | `status` | `ACTIVE`、`DISABLED` |
| `meeting_room` | `status` | `ENABLED`、`DISABLED` |
| `booking` | `status` | `ACTIVE`、`CANCELLED` |
| `booking_slot` | `occupancy_state` | `ACTIVE`、`CANCELLED_CURRENT_SLOT_HOLD` |
| `booking_audit_log` | `operation_type` | `CREATE`、`UPDATE`、`CANCEL` |
| `booking_audit_log` | `actor_role_snapshot` | `USER`、`ADMIN` |
| `idempotency_record` | `operation_type` | `CREATE_BOOKING` |
| `idempotency_record` | `processing_status` | `PROCESSING`、`SUCCEEDED`、`FAILED` |

不在 DDL 中加入预约时长、30 分钟边界、未来 14 天、会议室启用校验、管理员原因必填等规则；它们依赖当前时间、操作人身份或跨表信息，应由 Service 层在事务内执行，避免不透明或难维护的数据库约束。

## 5. 逻辑外键策略

V1 不建立任何 `FOREIGN KEY`。这是 V0.2 已确认的策略：避免迁移、数据修复及运行时槽清理受到物理引用约束，同时保留历史数据。

完整性由后端保证：

- 所有关联 ID 类型一致且已建立必要的查询索引。
- 创建/变更预约校验会议室真实存在且状态为 `ENABLED`。
- 预约人、取消人、修改人和审计操作人均由服务端认证上下文确定。
- `sys_user`、`meeting_room`、`booking`、`booking_audit_log` 禁止物理删除；取消预约仅更新 `booking` 状态。
- `booking_slot` 是可清理运行时数据；`idempotency_record` 仅在终态且超过 24 小时后可清理，`PROCESSING` 记录必须先走恢复流程。

## 6. Flyway 版本策略

- `V1__init_schema.sql` 只创建初始六表、索引、唯一约束和 CHECK 约束。
- V1 假定 Flyway 已连接到一个存在但无业务表的 MySQL 8 目标数据库；Flyway 自身会建立 schema history 表，不依赖手工建表。
- 任何字段、索引、状态值或约束变化都以新的递增 Flyway 版本实现；禁止改写已经执行过的 V1。
- V1 不插入任何用户、管理员、会议室或测试数据。

## 7. 幂等事务、失败分类与锁定规则

创建预约使用两段式幂等模型：

1. 已通过 HTTP 协议和请求格式校验的创建预约命令，先在独立短事务插入并提交 `PROCESSING` 的 `idempotency_record`。
2. 业务事务以 `SELECT ... FOR UPDATE` 锁定该幂等记录，随后在同一事务内创建 `booking`、批量插入 `booking_slot`、写 `booking_audit_log`，并更新为 `SUCCEEDED`，保存稳定的首次 HTTP 状态码和 `response_body`。
3. 同键请求读取到 `PROCESSING` 时不得自行再次创建；只能等待后重新查询，或返回“仍在处理/结果暂时无法确认”。即使处于首业务事务回滚和 `FAILED` 短事务提交之间，也不得再次执行创建。
4. 确定性业务失败必须先让业务事务回滚，再在独立短事务更新为 `FAILED`，保存稳定的 HTTP 状态码、`failure_code` 和 `response_body`。
5. 基础设施异常不能伪装成确定性 `FAILED`。超时的 `PROCESSING` 只能由恢复任务先取得行锁、确认状态仍是 `PROCESSING` 后终结。
6. 后续 Spring/MyBatis 实现不得在 rollback-only 的事务中捕获 `DuplicateKeyException` 后继续查询或更新幂等结果；必须在事务结束后使用独立事务或无事务查询。

### 7.1 领取前允许直接返回的失败

以下 HTTP 协议、请求格式层失败发生在请求尚不能形成合法“创建预约命令”之前，允许不领取、不查询，也不持久化 `idempotency_record`：

- JSON 无法解析；
- `Idempotency-Key` 缺失；
- 字段类型无法转换；
- 请求本身无法形成合法的创建预约命令。

这些失败直接返回相应的 4xx。它们没有进入幂等业务处理范围，因此不要求在 24 小时内按幂等键重放首次失败结果。

### 7.2 领取后必须持久化的确定性业务失败

当请求已经形成合法创建预约命令并领取 `idempotency_record` 后，以下稳定业务失败必须进入幂等流程：

- 目标会议室不存在或已停用；
- 超过未来 14 天；
- 开始、结束时间不符合业务规则；
- 时长超过 5 小时；
- 跨日；
- 时间槽冲突；
- 其他可稳定判定的业务规则失败。

首次处理失败时，业务事务回滚后必须通过独立短事务将原记录终结为 `FAILED`，并保存稳定的 `response_http_status`、`failure_code`、`response_body`。同一用户在 24 小时内使用相同操作类型、相同幂等键、相同请求哈希重试时，必须返回这一次首次失败结果；相同键但不同哈希仍应拒绝。

基础设施异常，例如数据库不可用、连接中断或应用进程异常，不得伪装为确定性业务 `FAILED`；记录保留为 `PROCESSING` 并按恢复机制处理。

## 8. idempotency_record 清理与恢复规则

常规过期清理任务只允许删除同时满足以下条件的记录：

```text
processing_status IN ('SUCCEEDED', 'FAILED')
AND expires_at < 当前时间
```

`PROCESSING` 记录即使已超过 `expires_at`，也不得由常规清理任务直接删除。异常 `PROCESSING` 必须按以下恢复流程处理：

1. 检查 `processing_started_at` 是否已超过恢复阈值；
2. 使用 `SELECT ... FOR UPDATE` 尝试取得该记录行锁；
3. 取得锁后确认不存在仍在执行且持有该记录锁的业务事务；
4. 再次确认 `processing_status` 仍为 `PROCESSING`；
5. 在恢复事务中将其终结为稳定 `FAILED`，保存相应状态码、失败码与响应体；
6. 终态记录随后才可在常规过期清理任务中按 `expires_at` 删除。

该顺序防止错误删除正在处理的创建请求，也保证网络超时后的原幂等键查询始终能得到“处理中、成功或稳定失败”之一。

## 9. booking_slot 生命周期

正常预约为每个 30 分钟时间段插入一个 `ACTIVE` 槽。进行中取消时，当前槽保留并更新为 `CANCELLED_CURRENT_SLOT_HOLD`，后续槽删除；当前槽结束后，由清理任务删除过去的运行时槽。`booking` 和 `booking_audit_log` 长期保留完整历史，因此清理槽不会丢失预约审计事实。
