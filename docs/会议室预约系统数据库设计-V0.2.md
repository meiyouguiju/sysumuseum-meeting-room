# 会议室预约系统数据库设计

文档版本：V0.2  
状态：数据库详细设计基线  
依据：[MVP业务规则确认文档 V1.0](会议室预约系统MVP业务规则确认文档-V1.0.md)  
范围：仅逻辑设计；不包含 SQL DDL、迁移脚本或业务代码。

## 1. 总体结论

MVP 保留六张核心表：

1. `sys_user`
2. `meeting_room`
3. `booking`
4. `booking_slot`
5. `booking_audit_log`
6. `idempotency_record`

不建立 `sys_role`、`sys_user_role`。MVP 只有互斥的 `USER` 与 `ADMIN` 两种角色，使用 `sys_user.role_code` 更简单、查询更直观。出现一人多角色、资源级角色或第三种以上稳定角色后，再演进为独立 RBAC 表。

不建立任何 MySQL `FOREIGN KEY`。表之间采用逻辑关联：所有关联 ID 均使用完全一致的 `BIGINT UNSIGNED` 类型；写入前由 Service 层校验关联对象与权限；各查询关联列必须有索引。`sys_user`、`meeting_room`、`booking`、`booking_audit_log` 永不物理删除；`booking_slot` 与过期 `idempotency_record` 可以清理。

业务时区固定为 `Asia/Shanghai`。所有业务时间使用 `DATETIME(0)`，Java 领域对象使用 `LocalDateTime`，仅在 API 入口、系统时钟和日志边界显式按 `Asia/Shanghai` 转换。不得将业务预约时间映射为 MySQL `TIMESTAMP` 或隐式使用数据库会话时区，以避免 8 小时时差。

## 2. 通用字段与时间规则

- 主键均为 `BIGINT UNSIGNED`；所有 `*_user_id`、`room_id`、`booking_id` 与其被引用主键类型完全一致。
- 业务时间使用 `DATETIME(0)`，精确到秒即可；预约规则保证分钟仅为 `00` 或 `30`。
- `created_at`、`updated_at`、审计发生时间也使用 `DATETIME(0)`，由服务端按北京时间写入。
- `DATETIME` 不携带时区，故 JDBC 连接、JVM 默认时区、序列化反序列化均须统一为 `Asia/Shanghai`；日志中的跨系统事件可另用 `Instant`，但不能替代预约业务字段。

## 3. 表详细设计

### 3.1 `sys_user`

**职责：** 映射中山大学统一身份认证用户，保存当前系统角色、状态及同步资料。

| 字段 | 类型 | NULL | 默认值 | 类别 | 存在原因 |
| --- | --- | --- | --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 否 | 无 | 技术 | 内部主键与所有用户逻辑关联的统一目标 |
| `auth_provider` | `VARCHAR(32)` | 否 | `'SYSU_SSO'` | 业务事实 | 区分正式中大认证与测试期替代认证 |
| `external_subject` | `VARCHAR(128)` | 否 | 无 | 业务事实 | 认证方提供的稳定用户唯一标识 |
| `login_name` | `VARCHAR(64)` | 否 | 无 | 业务事实 | 展示、排查与同步使用，不是身份唯一依据 |
| `display_name` | `VARCHAR(100)` | 否 | 无 | 业务事实 | 当前姓名 |
| `department_name` | `VARCHAR(200)` | 是 | `NULL` | 业务事实 | 从身份系统同步的部门 |
| `role_code` | `VARCHAR(16)` | 否 | `'USER'` | 业务事实 | `USER` 或 `ADMIN` |
| `status` | `VARCHAR(16)` | 否 | `'ACTIVE'` | 业务事实 | `ACTIVE` 或 `DISABLED` |
| `last_synced_at` | `DATETIME(0)` | 是 | `NULL` | 技术/审计 | 最近身份信息同步时间 |
| `created_at` | `DATETIME(0)` | 否 | 当前时间 | 审计 | 建档时间 |
| `updated_at` | `DATETIME(0)` | 否 | 当前时间 | 审计 | 最后同步或维护时间 |

- 主键：`id`
- 唯一约束：`UNIQUE(auth_provider, external_subject)`
- 不建立 `UNIQUE(auth_provider, login_name)`，因为 `login_name` 不承担稳定身份语义。
- 首期无需普通索引；管理员用户管理确有按状态分页时再增加 `INDEX(status, id)`。
- 不物理删除；停用即可。所有被引用关系均为逻辑关联。

**职责：** 保存会议室当前配置、启用/停用状态和使用须知；历史预约永远指向原会议室。

| 字段 | 类型 | NULL | 默认值 | 类别 | 存在原因 |
| --- | --- | --- | --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 否 | 无 | 技术 | 主键 |
| `name` | `VARCHAR(120)` | 否 | 无 | 业务事实 | 会议室名称 |
| `location` | `VARCHAR(200)` | 否 | 无 | 业务事实 | 地点 |
| `capacity` | `SMALLINT UNSIGNED` | 否 | 无 | 业务事实 | 容量；仅产生超额警告 |
| `facilities_text` | `TEXT` | 是 | `NULL` | 业务事实 | 设备说明 |
| `usage_notice` | `TEXT` | 是 | `NULL` | 业务事实 | 前端展示的使用须知 |
| `status` | `VARCHAR(16)` | 否 | `'ENABLED'` | 业务事实 | `ENABLED`、`DISABLED` |
| `sort_order` | `INT` | 否 | `0` | 业务事实 | 日程排列顺序 |
| `created_at` | `DATETIME(0)` | 否 | 当前时间 | 审计 | 创建时间 |
| `created_by_user_id` | `BIGINT UNSIGNED` | 是 | `NULL` | 审计 | 创建管理员，逻辑关联 `sys_user.id` |
| `updated_at` | `DATETIME(0)` | 否 | 当前时间 | 审计 | 更新时间 |
| `updated_by_user_id` | `BIGINT UNSIGNED` | 是 | `NULL` | 审计 | 修改管理员，逻辑关联 `sys_user.id` |

- 主键：`id`
- 唯一约束：`UNIQUE(name)`；会议室不删除，因此名称全表永久唯一可避免历史歧义。
- 普通索引：`INDEX(status, sort_order, id)`，支持日程会议室列表。
- 不物理删除。Service 层在创建预约或变更会议室时，必须确认 `room_id` 存在且状态为 `ENABLED`。停用会议室保留未来与历史预约，但禁止新增预约及将其他预约改入该会议室。

### 3.3 `booking`

**职责：** 预约的主业务事实、取消事实和乐观锁控制；它是预约历史的长期来源，不因取消而删除。

| 字段 | 类型 | NULL | 默认值 | 类别 | 存在原因 |
| --- | --- | --- | --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 否 | 无 | 技术 | 主键 |
| `booking_no` | `VARCHAR(32)` | 否 | 无 | 业务事实 | 稳定、可对外展示的预约编号 |
| `room_id` | `BIGINT UNSIGNED` | 否 | 无 | 业务事实 | 原始预约会议室，逻辑关联 `meeting_room.id` |
| `organizer_user_id` | `BIGINT UNSIGNED` | 否 | 无 | 业务事实 | 预约人；必须由服务端认证上下文取得 |
| `organizer_name_snapshot` | `VARCHAR(100)` | 否 | 无 | 业务事实 | 创建时预约人姓名快照 |
| `subject` | `VARCHAR(200)` | 否 | 无 | 业务事实 | 必填会议主题 |
| `attendee_count` | `SMALLINT UNSIGNED` | 是 | `NULL` | 业务事实 | 非必填预计人数 |
| `participants_text` | `TEXT` | 是 | `NULL` | 业务事实 | 非结构化参会人员；仅预约人和管理员可见 |
| `description` | `TEXT` | 是 | `NULL` | 业务事实 | 会议说明 |
| `start_time` | `DATETIME(0)` | 否 | 无 | 业务事实 | 原始开始时间 |
| `end_time` | `DATETIME(0)` | 否 | 无 | 业务事实 | 原始结束时间 |
| `status` | `VARCHAR(16)` | 否 | `'ACTIVE'` | 业务事实 | `ACTIVE`、`CANCELLED` |
| `cancelled_at` | `DATETIME(0)` | 是 | `NULL` | 业务事实 | 取消生效时间 |
| `cancelled_by_user_id` | `BIGINT UNSIGNED` | 是 | `NULL` | 审计/业务事实 | 取消操作人，由服务端确定 |
| `cancel_reason` | `VARCHAR(500)` | 是 | `NULL` | 审计/业务事实 | 管理员取消他人预约时必填 |
| `version` | `INT UNSIGNED` | 否 | `1` | 技术 | 乐观锁版本，修改与取消均递增 |
| `last_modified_at` | `DATETIME(0)` | 否 | 当前时间 | 审计 | 最后修改或取消时间 |
| `last_modified_by_user_id` | `BIGINT UNSIGNED` | 是 | `NULL` | 审计 | 最后操作人，由服务端确定 |
| `created_at` | `DATETIME(0)` | 否 | 当前时间 | 审计 | 创建时间 |
| `updated_at` | `DATETIME(0)` | 否 | 当前时间 | 审计 | 最后持久化时间 |

- 主键：`id`
- 唯一约束：`UNIQUE(booking_no)`
- 普通索引：
  - `INDEX(room_id, start_time, id)`：某会议室某日/历史预约。
  - `INDEX(organizer_user_id, start_time, id)`：我的预约。
  - `INDEX(start_time, room_id, id)`：管理员按日期范围列表与导出。
  - `INDEX(status, start_time, id)`：管理员按状态与时间查看预约。

`FINISHED` 不持久化。已结束由 `status = 'ACTIVE' AND end_time <= 当前北京时间` 动态计算；正在进行由 `status = 'ACTIVE' AND start_time <= 当前时间 < end_time` 动态计算。取消记录保留原始会议室、原始时间和主题，不能为释放槽位而改写。

修改规则对应的持久化边界：

- 未开始：管理员可修改全部允许字段；普通用户只能修改本人预约。
- 已开始未结束：管理员只能修改主题、预计人数、参会人员、说明等非时间字段；不能修改会议室、开始时间、结束时间。普通用户不能再修改。
- 已结束：USER 与 ADMIN 都不能修改业务字段，仅允许查看、审计和导出。

### 3.4 `booking_slot`

**职责：** 会议室当前/未来可用性的运行时占用表。每行代表一个不可重复占用的 30 分钟槽，是并发冲突的最终一致性边界，不承担长期历史。

| 字段 | 类型 | NULL | 默认值 | 类别 | 存在原因 |
| --- | --- | --- | --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 否 | 无 | 技术 | 主键 |
| `booking_id` | `BIGINT UNSIGNED` | 否 | 无 | 业务事实 | 对应预约，逻辑关联 `booking.id` |
| `room_id` | `BIGINT UNSIGNED` | 否 | 无 | 业务事实 | 冗余保存以直接实现资源唯一占用 |
| `slot_start` | `DATETIME(0)` | 否 | 无 | 业务事实 | 30 分钟槽开始时间 |
| `occupancy_state` | `VARCHAR(32)` | 否 | `'ACTIVE'` | 运行时事实 | `ACTIVE` 或 `CANCELLED_CURRENT_SLOT_HOLD` |
| `created_at` | `DATETIME(0)` | 否 | 当前时间 | 技术/审计 | 槽写入时间 |
| `updated_at` | `DATETIME(0)` | 否 | 当前时间 | 技术/审计 | 槽状态最后更新时间 |

- 主键：`id`
- 关键唯一约束：`UNIQUE(room_id, slot_start)`，同一会议室同一槽只能由一个预约占用。
- 辅助唯一约束：`UNIQUE(booking_id, slot_start)`，防止一个预约重复生成同一槽。
- 普通索引：`INDEX(slot_start, room_id, booking_id)`，支持某日全会议室日程。
- 不保存 `slot_end`：固定粒度下它恒等于 `slot_start + 30分钟`，保存会造成冗余和潜在不一致。

进行中取消的生命周期：预约 10:00～12:00 在 10:12 取消时，同一事务内将 `booking` 改为 `CANCELLED`；删除 10:30、11:00、11:30 槽；保留 10:00 槽并将状态更新为 `CANCELLED_CURRENT_SLOT_HOLD`。日程把该槽展示为“本槽结束前不可预约”，不展示已取消预约的主题。到 10:30 后，清理任务删除 `slot_start` 早于当前 30 分钟槽开始的运行时槽。历史由 `booking` 与审计表保存。

### 3.5 `booking_audit_log`

**职责：** 统一保存创建、修改、取消的不可变审计；满足管理员改/取消他人预约留痕、每次修改保存完整前后内容以及槽变化追溯。

采用“固定元数据字段 + `before_json` + `after_json`”，不另建 `booking_change_log`。本项目审计重点是完整追溯而非对历史字段做复杂分析，JSON 快照比为每个字段复制历史列更稳定、易维护。

- 主键：`id`
- 普通索引：
  - `INDEX(booking_id, occurred_at, id)`：预约全量审计。
  - `INDEX(actor_user_id, occurred_at, id)`：管理员操作排查。
  - `INDEX(operation_type, occurred_at, id)`：按操作类型排查。
- 审计表不物理删除，也不对 JSON 内部字段建立索引。

**职责：** 为创建预约提供 24 小时严格幂等、重复结果返回和网络超时后的原键查询。`operation_type` 在 MVP 固定为 `CREATE_BOOKING`，但保留字段以支持未来其他幂等动作。

| `processing_status` | `VARCHAR(16)` | 否 | `'PROCESSING'` | 技术 | `PROCESSING`、`SUCCEEDED`、`FAILED` |

| `response_body` | `JSON` | 是 | `NULL` | 技术 | 首次完成响应体，供重复请求与查询复用 |
| `failure_code` | `VARCHAR(64)` | 是 | `NULL` | 技术 | 业务失败的稳定错误码 |
| `processing_started_at` | `DATETIME(0)` | 否 | 当前时间 | 技术 | 领取处理权的时间，用于异常处理中状态检测 |
| `completed_at` | `DATETIME(0)` | 是 | `NULL` | 技术 | 终态写入时间 |
| `created_at` | `DATETIME(0)` | 否 | 当前时间 | 技术 | 初次领取时间 |
| `expires_at` | `DATETIME(0)` | 否 | 无 | 技术 | 固定为创建后 24 小时 |

- 唯一约束：`UNIQUE(operation_type, user_id, idempotency_key)`。

## 4. 幂等事务模型复核

### 4.1 结论：调整为“两段事务、三种明确状态”

V0.1 的“幂等记录与预约完全同一事务”能保证成功原子性，但存在两个实际问题：

1. 首事务提交前，其他请求看不到 `PROCESSING`，该状态几乎没有对外意义。
2. 校验失败或槽唯一冲突会回滚整个事务，`FAILED` 无法持久化，因而同一键在 24 小时内无法稳定返回首次失败结果，也无法拒绝后续不同请求体。

V0.2 保留 `PROCESSING`、`SUCCEEDED`、`FAILED`，但将其职责收敛为以下两段：

1. **领取事务（短事务）**：插入并提交 `PROCESSING` 幂等记录，永久占用该用户该操作的幂等键 24 小时。
2. **业务事务**：锁定该幂等记录，创建 `booking`、插入 `booking_slot`、写 `booking_audit_log`，并在同一事务中将幂等记录更新为 `SUCCEEDED` 和首次响应；成功预约与成功响应仍是原子提交。
3. **确定性业务失败事务（短事务）**：若业务事务因参数规则、会议室状态或槽冲突回滚，在业务事务外用新事务将原记录更新为 `FAILED`，保存首个失败响应。不得在已标记 rollback-only 的事务中继续写或查询。

这比把全部状态都塞进一个事务多一次很小的记录写入，但能真实支持“处理中查询”、24 小时内同键不同体拒绝，以及稳定返回首次失败结果，仍适合小型内部 MVP。

### 4.2 状态的真实生命周期

| 状态 | 是否可被查询到 | 何时出现 | 后续变化 |
| --- | --- | --- | --- |
| `PROCESSING` | 是 | 领取事务成功提交后 | 业务成功变 `SUCCEEDED`；确定性失败变 `FAILED`；异常中断由恢复机制收敛 |
| `SUCCEEDED` | 是 | 预约、槽、审计和成功响应同一业务事务提交时 | 到 `expires_at` 后清理 |
| `FAILED` | 是 | 业务事务回滚后，独立短事务记录稳定业务失败响应 | 到 `expires_at` 后清理 |

`FAILED` 只保存可稳定复现、应返回给用户的业务失败，例如时间槽冲突、未来 14 天校验失败、会议室已停用、字段校验失败。数据库不可用、应用崩溃等未知基础设施失败不应伪造为业务 `FAILED`；它们暂留 `PROCESSING`，等待恢复或结果查询。

### 4.3 同键并发请求

1. **首事务成功提交：** 第二个相同请求在唯一键或幂等记录锁上等待；获得记录后，若哈希相同且状态为 `SUCCEEDED`/`FAILED`，直接返回首次响应；哈希不同则拒绝。
2. **首业务事务回滚：** 领取记录仍保留为 `PROCESSING`，随后失败短事务将其置为 `FAILED`。第二个请求应读取最终失败响应，不得自行再次创建。
3. **第二请求自身等待超时：** 返回“处理结果暂时无法确认/仍在处理”，不视为创建失败；前端仅用相同 `Idempotency-Key` 调用结果查询接口，不使用新键重提。

### 4.4 异常 `PROCESSING` 的恢复

业务事务在写预约、时间槽、审计和状态终结时持有该幂等记录行锁。若进程崩溃或事务异常回滚，数据库不会留下部分预约提交；但短领取事务留下的记录可能停留在 `PROCESSING`。

建议每分钟由轻量恢复任务处理超过合理处理阈值（例如 2 分钟）的 `PROCESSING` 记录：先以行锁读取；若能取得锁且状态仍为 `PROCESSING`，说明没有活跃业务事务持锁，可将其终结为系统中断的 `FAILED` 响应。网络超时查询对此状态返回“结果暂时无法确认”，待恢复完成后可查询到明确失败结果。

MVP 无外部副作用（例如邮件、短信），因此上述恢复不会造成“数据库创建一次、外部通知多次”的问题。

### 4.5 Spring Boot + MyBatis 实现边界

- 捕获 `DuplicateKeyException` 或 `DataIntegrityViolationException` 后，不能在同一个声明式业务事务内继续查询首次结果；该事务可能已被标记为 rollback-only。
- 推荐由非事务编排层捕获异常，或在原事务确实结束回滚后，再调用独立的 `REQUIRES_NEW` 查询/终结方法。
- 查询首次结果应在独立只读事务或无事务 Mapper 调用中执行，并固定带 `operation_type='CREATE_BOOKING'`、`user_id`、`idempotency_key`。
- 不能把“捕获唯一键异常后查询并返回首次响应”与槽写入、预约修改混在同一个 `@Transactional` 方法中。
- 槽冲突与幂等键冲突必须区分：前者是业务 `FAILED`；后者是读取同键首次处理状态或拒绝同键不同请求。

## 5. 事务边界

### 5.1 创建预约

1. 短事务领取或读取 `idempotency_record`；校验同键请求哈希。
2. 如已有 `SUCCEEDED`/`FAILED`，直接返回首次响应；如已有活动 `PROCESSING`，等待、查询或返回处理中结果。
3. 新键进入业务事务：校验当前认证用户、会议室存在且启用、14 天、半小时粒度、时长、跨日及预约规则。
4. 插入 `booking`，批量插入 `booking_slot`，利用 `UNIQUE(room_id, slot_start)` 裁决冲突。
5. 写 `CREATE` 审计快照，将幂等记录更新为 `SUCCEEDED` 并保存首次响应，整体提交。
6. 确定性失败时，业务事务回滚；在新短事务内将同一记录写为 `FAILED`。

### 5.2 修改预约

单事务完成：锁定预约，校验 `version`、身份、状态及时间阶段，保存前快照，按规则修改字段并递增版本，必要时原子重建未来槽；写 `UPDATE` 前后快照与槽变化后提交。

- 未开始且时间/会议室变更：删除该预约未开始的旧槽后插入新槽；任何槽冲突则回滚，旧槽和原预约保持不变。
- 进行中：管理员只允许非时间字段更新，不得删除、重建或改变任意槽；普通用户拒绝修改。
- 已结束：所有角色拒绝修改业务字段。

### 5.3 取消预约

单事务完成：锁定预约，校验权限与未结束条件，记录前快照，更新为 `CANCELLED`、递增版本；未开始则删除全部槽，进行中则删除后续槽并标记当前槽为 `CANCELLED_CURRENT_SLOT_HOLD`；写 `CANCEL` 审计后提交。

## 6. 关系、索引与逻辑关联

文字 ER 图：

```text
[sys_user] 1 ───< organizer / operator >─── N [booking]
     │                                           │
     ├──< actor / target_owner >── N [booking_audit_log]
     └──< requester >───────────── N [idempotency_record]

[meeting_room] 1 ───< room >────── N [booking] 1 ───< occupies >── N [booking_slot]
     └──────────────────────────────────────────< room >────────────┘
```

所有箭头均为逻辑关联，没有物理外键。Service 层责任如下：

- 创建或修改预约时校验 `room_id` 存在、启用且可预约。
- `organizer_user_id` 只从认证上下文取得，拒绝前端指定。
- `cancelled_by_user_id`、`last_modified_by_user_id`、审计 `actor_user_id` 均从认证上下文取得。
- 插入槽与审计前确认目标 `booking` 存在；审计的 `target_owner_user_id` 从预约主记录取得。
- 不允许物理删除用户、会议室、预约和审计；删除技术槽与过期幂等记录不需要删除其父业务记录。

最终索引和唯一约束：

| 表 | 约束或索引 |
| --- | --- |
| `sys_user` | `PK(id)`；`UNIQUE(auth_provider, external_subject)` |
| `meeting_room` | `PK(id)`；`UNIQUE(name)`；`INDEX(status, sort_order, id)` |
| `booking` | `PK(id)`；`UNIQUE(booking_no)`；`INDEX(room_id, start_time, id)`；`INDEX(organizer_user_id, start_time, id)`；`INDEX(start_time, room_id, id)`；`INDEX(status, start_time, id)` |
| `booking_slot` | `PK(id)`；`UNIQUE(room_id, slot_start)`；`UNIQUE(booking_id, slot_start)`；`INDEX(slot_start, room_id, booking_id)` |
| `booking_audit_log` | `PK(id)`；`INDEX(booking_id, occurred_at, id)`；`INDEX(actor_user_id, occurred_at, id)`；`INDEX(operation_type, occurred_at, id)` |
| `idempotency_record` | `PK(id)`；`UNIQUE(operation_type, user_id, idempotency_key)`；`INDEX(expires_at)` |

## 7. 数据生命周期与风险

| 数据 | 删除策略 |
| --- | --- |
| `sys_user` | 永不物理删除，停用保留 |
| `meeting_room` | 永不物理删除，停用保留 |
| `booking` | 永不物理删除；`ACTIVE`、`CANCELLED` 长期保留 |
| `booking_audit_log` | 永不物理删除 |
| `booking_slot` | 过去槽由清理任务删除；它不是历史来源 |
| `idempotency_record` | `expires_at` 过期后定期物理清理 |

主要风险与控制：

1. 全天均可预约，实际每天有 48 个时间槽；前端必须能选择非 08:30～17:30 时段。
2. 查询已结束的当天日程应基于 `booking`，不能依赖已清理的 `booking_slot`。
3. 首次幂等响应体必须稳定，不包含会随当前时间变化的派生字段。
4. 无物理外键意味着引用完整性完全依赖 Service 层；写操作必须集中在受测试的业务服务，不允许绕过服务层直接写核心表。
5. `PROCESSING` 恢复任务必须先锁记录再终结，避免误判仍在执行的业务事务。

## 8. 可进入 DDL 阶段的结论

本 V0.2 已明确表、字段、逻辑关联、约束、索引、时间模型、事务边界和清理策略，没有阻止生成 SQL DDL 的未决业务问题。
